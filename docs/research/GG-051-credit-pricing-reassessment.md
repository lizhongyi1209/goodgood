## token 能否换算为明确报价

BytePlus 公开估算涉及 `(输入视频时长 + 输出视频时长) × 输出宽 × 输出高 × 输出帧率 / 1024`，并提示部分参考视频任务有最低 token 消耗，实际以返回的 `usage.completion_tokens` 为准。模型、版本与模式需分别核实；不把此公式直接套用到 O1Key 的 Seedance 2.5 或 HC 线路。

这支持一个有条件的推论：固定规格、输入成本可控时，可以将 token 估算转成固定积分报价；但仅用输出秒数会遗漏参考视频、最低消耗、音频或其他模型相关收费项。视频 token 也不能按提示词字数理解。

## 第一轮建议及适用边界

保留单一积分单位及现有兑换基准；个人和企业仍按原有归属分别记账。图片按张；视频按模型/明确线路、分辨率、音频模式、输出时长和实际计费输入计算总积分。数量与提示词分段应逐任务报价后求和；不同规格不能简单乘同一个单价。

优先采用提交前固定报价：服务端根据已验证成本规则计算，冻结该报价及版本，成功交付后收取原报价，明确失败释放。标准/备用分别核算，切换应重新报价，遵守 ADR 0049 不自动切线路。每个独立视频任务单独预留/关闭；多条视频部分失败时，仅成功交付任务扣费。此为待实施建议，不改变现有图片整批结算语义。

如某种模式无法可靠预估，才引入“预计 X，最多 Y”与上限预留，完成后按已披露规则结算、退还差额；不得静默超过用户同意的上限。缺失 usage 不视为零消耗，应进入明确的待对账策略。当前账本不直接支持这种部分结算，需要个人、企业成员预算、来源余额与幂等闭合一起设计。因此不建议第一阶段所有生成都实行事后 token 浮动扣费。

## 如何从成本推导积分

按规格计算完整交付成本 C：实际上游净支出、存储/交付成本，以及失败未退费、必要重试等损耗分摊。存在多类 token 时分别乘对应单价再相加；不得随意把不同价格的输入/输出 token 合成一个 total_tokens 单价。

令 v 为平台每发出一个可消费积分的实际收入，g 为此成本口径下的目标贡献毛利率：

`最低积分报价 = ceil(C / (v × (1 − g)))`

如果手续费按营收比例收取，应从收入端扣除或在公式中单列，避免漏算/重复计算。最终售价还需经用户价值与竞品可比人民币成本验证；成本公式给出底线，不保证市场接受。

仅作算例：假设某条视频完整成本 1.20 元，v=0.02 元，目标毛利率 40%，则报价 100 积分，收入 2 元。若分销/赠送使 v 降为 0.016 元，则同样目标需 125 积分；仍卖 100 积分时毛利率只有 25%。这些数值不是 O1Key 报价，也不是获确认目标。

保留 1 积分=基准 0.02 元足以覆盖视频，无需为 token 改成小数积分。后台用精确货币小单位保存成本，按已公布规则在每个独立任务总价处取整。未来更细粒度业务确有需要时再讨论单位变化。

定价评估应分模型和线路核对全范围成本，尤其 4K、长视频、视频参考和最深销售折扣。不能只用平均用户行为让高成本规格长期亏损。欢迎积分、促销赠送和下游折扣应纳入收入/获客成本模型；不擅自降低现有积分购买力或增加过期限制。

## 第二轮：多线路与高波动成本下的建议（取代第一轮默认策略）

用户补充：同一个 Banana 模型有三条 O1Key 线路，前两条全分辨率固定价，第三条按官方价格折扣后的用量计费；视频多数按 token，Seedance 2.0 同为 4K 的实际费用可能相差数十元。此为用户提供的经营事实，本轮未读取其账户账单；不把差异全部解释成同一完整参数下的随机波动。

建议以“产品模型 + 计费线路 + 适用条件”为定价对象。保留一个积分单位，同时支持固定积分/张与按用量积分。不能将同模型三条线路绑定到一条固定价，也不能在固定价失败后静默切到按量线路。Banana 新线路开放需另行明确产品参数与映射，不能从已有视频两线实现推定已经支持。

| 场景 | 建议消费规则 | 前台表达 |
| --- | --- | --- |
| Banana 固定价线路 A/B | 各自设置固定积分/张；可同价也可不同价 | 本次 X 积分 |
| Banana 官方折扣按量线路 C | 分类型实际用量 × 提交时锁定积分费率 | 按量计费、预估范围、最高扣费 |
| Seedance 等高波动线路 | 依准确模型/线路/规格匹配用量费率，再按实际用量结算 | 按量计费、预估范围、最高扣费 |

### 进价与售价分别管理

进价规则：固定元/张，或官方输入/输出/缓存/音频等单价表 × O1Key 采购折扣，记录币种、汇率口径、生效时间、最低计费规则和精确 usage 字段。按量不总是 token，也应保留按秒等明确单位。不同类别费率不能用 total_tokens 粗暴合并。

售价规则：固定积分，或各计费类别的积分/百万 tokens。站长可根据成本和加价倍率生成建议费率，但发布的是独立、版本化的销售规则：

`建议积分/百万 tokens = 采购价（元/百万 tokens）× 销售倍率 ÷ 基准每积分金额`

`最终积分 = ceil(Σ(各计费类别实际用量 × 已锁定积分费率 / 对应单位基数) + 已披露固定服务费)`

最低计费应作用在该模型规则定义的位置；服务费默认可为零，仅在有明确产品决定时启用。中间费率保留精度，每条独立任务总额取整。不可在用户完成后用最新官网价、最新倍率或临时重试费用重新计算其售价。

纯算例：假设一条线路采购价为 12 元/百万 tokens，销售费率为 1000 积分/百万 tokens；在 0.02 元/积分的基准收入下，0.5M tokens 收 500 积分（10 元），2M 收 2000 积分（40 元），对应采购成本为 6/24 元。这里只计算上游毛利，尚未扣除其他损耗；不代表 O1Key 实价。加价 25% 对应毛利率 20%，面板须区分加价倍率与毛利率；分销折扣与赠送后的实际积分收入仍需复核。

### 预留、扣费上限与上游风险

预估价格只供预算参考，冻结单位费率才是按量定价承诺。消费者预付模式建议提交前展示预估范围及最高扣费，按最高金额原子预留个人或企业预算。完成后可靠 usage 到达时原子扣除实际积分并释放余额，退款保留来源比例/规则；每个独立任务只关闭一次，成功媒体与计费状态分开。

最高扣费必须由经验证的参数最坏上界或上游真正可执行的用量限制支持；预留余额、轮询进度、发送取消请求均不自动保证上游停止计费。P95/P99 或预估值加百分比不是硬上界。若上游没有硬上界/可靠取消，平台需明确接受超额差额风险，并限制开放规格或暂不开放该线路；用户授权额度过小也不能先启动再保证自动停止。

无法同时承诺“用户低上限、任何费用都不由平台承担、异步任务一定完成”。若以后选择不封顶实扣，应另设用户明确理解的后付费/授信产品及追缴规则，不能默认为现有预付积分体验。

账单迟到或 usage 缺失时进入“结果已完成，费用核算中”，不按零结算、不无限期冻结；实现前需确定最长核算期限与到期退款/平台承担的处理。对账更正形成新事件，不能重复扣费或无授权突破原上限。交付失败时客户释放与上游是否收费独立，损耗记入平台成本，不把内部重试多次成本默认转嫁客户。

### 站长定价面板的首版范围

| 面板部分 | 必需信息与操作 |
| --- | --- |
| 模型/线路列表 | 精确 provider 映射、固定/按量、适用参数、可用状态、当前版本与生效时间 |
| 采购成本 | 固定单价或分类 token 单价、官方价版本、采购折扣、币种/汇率、最低消耗、计费依据与核对时间 |
| 销售价格 | 固定积分或分类用量积分费率、按倍率生成建议、基准/最低实际收入下的利润预览 |
| 预估与开放边界 | 按规格估算、上界依据、最高可接受风险、usage 不完整的停用/待核算状态；不伪称能停止上游 |
| 试算与发布 | 无付费请求的模拟试算，旧新规则差异，立即/定时发布，停用新提交，审计记录 |
| 历史与对账 | 任务实际用量、成本、客户积分、超额差额/异常，旧版可查询；恢复旧费率发布为新版本 |

“即时更新”是服务端发布成功后新提交使用新版本，无须改代码重新部署。编辑草稿不影响在线价格。用户提交前的展示 quote 带有效期及规则版本；服务端发现版本变更则刷新报价并要求重新提交，不暗中换价。已经接受并预留的任务锁定单位费率、规则、参数和客户最高金额，即使排队也不追溯改价。紧急停用可阻止尚未派发的任务并释放，但不能使已经发送的 provider 费用消失。

只允许站长访问成本和发布操作，保留鉴权/CSRF/审计，规则发布需原子激活并使缓存失效。站长本人的面板发布操作是未来产品流程，不是要求开发对每次本地改动反复请求批准。成本同步可生成待发布草稿，不让第三方费率变化自动改用户价格。

### 与当前实现的差距和下一步

当前存在 `publishGenerationPriceVersion` 和不可变图片价格行，但没有站长定价界面，也没有多类别用量销售规则及部分预留结算。面板必须连接新的计价/结算契约，否则只能改展示数字，无法解决按量扣费。

本轮已形成可讨论的面板功能与混合计费方案，未将产品方向擅自视为已批准。后续确认范围后先写 ADR：定义可用量证据、预付上界/平台风险政策、报价失效与锁价、部分结算和站长发布。第一实现片段应覆盖一个固定线路与一个按量线路的面板发布→报价→预留→结算完整闭环，并验证个人/企业额度、来源余额、并发与失败，使用无真实 Worker 的隔离测试。

Runway 官方[追加积分说明](https://help.runwayml.com/hc/en-us/articles/23987639973267-Will-unused-credits-carry-over-after-my-billing-day)列出 1 积分=0.01 美元；按这一购买口径，上述 240/390 积分对应 2.40/3.90 美元，Seedance 2.0 4K 5 秒的 750 积分对应 7.50 美元。套餐分摊口径可能不同，此处不将套餐总价直接当成纯积分购买价。

### 本轮证据的结论与局限

上述三家创作产品公开的是按张、按输出秒，以及某些模型按输入视频秒加收的价目表；未查到其 Seedance 公布以返回 token 为准对消费者浮动扣分的规则。第二轮按实际 token 结算是对 GoodGood 高波动采购线路提出的方案，不应描述为已经核实的主流创作平台共同做法。

相对地，BytePlus ModelArk 的 Seedance API 官方资料按实际 token 消耗收费，不能将官方 API 成本与创作平台的消费价混为一谈。公开价目表未披露平台采购折扣、批量合同、成本分布或风险承担，无法证明其按秒价对 GoodGood 相同 O1Key 线路也有利润。

因此，后续可同时比较“按输出秒 + 输入秒的明码规则”与“按实际 token 结算”。能否采用前者，仍取决于 GoodGood 各线路的全范围实耗与可承担偏差；本轮先提供具体参照，不擅自决定一种规则或实现面板。
