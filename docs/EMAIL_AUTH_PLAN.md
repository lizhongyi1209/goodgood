# GoodGood 自建邮箱验证码登录：首版方案与实施计划

- 日期：2026-09-10；任务：[GG-029](tasks/GG-029-email-otp-plan.md)。
- 状态：P0 首轮真信和真实应用登录闭环已验证，P1/P2 与 P3 发布准备代码已在 GG-029
  隔离本地栈完成；完整跨邮箱/跨时段矩阵、生产演练/秘密安装与 P4 生产切换尚未完成。
- 决策：[ADR 0045](decisions/0045-goodgood-owned-email-otp.md)。
- 目标：支持日常注册、登录、退出、审核与故障处理，达到现有 controlled alpha 的上线要求。

## 1. 首版范围

只提供邮箱验证码登录。输入邮箱、收取六位数字、验证成功即登录；首次验证成功自动注册。
任何能正常收取邮件的受支持邮箱都可以使用，包括 Gmail；不提供 Google 一键登录。
新用户仍为 pending，领取一次 100 欢迎积分，站长审核后才能创作。现有 active/suspended、
管理员角色、资产归属和积分账本继续由 GoodGood 管理，认证改造不改变这些规则。

| 首版必须完成 | 首版延后 |
| --- | --- |
| 邮箱输入、验证码输入、重发、修改尚未提交的邮箱、退出 | Google/微信/手机/密码登录 |
| 手机浏览器布局、粘贴、数字键盘、返回创作现场 | 原生 App、SSO、多身份源绑定 |
| 保持登录、过期后原地重新登录 | 设备列表、自助管理全部设备 |
| 验证码过期/一次性/防猜测、发信限流与总量上限 | 常驻 CAPTCHA、复杂风险评分、设备指纹 |
| 邮件失败/迟到提示、发送记录排查、人工支持入口 | 多邮件供应商自动切换、营销邮件系统 |
| 账户审核/暂停/恢复；维护命令撤销指定账号全部会话 | 自助改绑邮箱、遗失邮箱自动找回、MFA/passkeys |
| 审计脱敏、短期记录清理、备份与兼容切换 | 自动注销与完整 C6 生命周期 |

这些延期是功能取舍，不能省略首版的验证码校验、限流或权限隔离。
对不能再访问原邮箱的用户，首版只能人工受理；不承诺立即恢复，不能凭聊天声明或新邮箱
直接改绑。站长邮箱建议在邮箱服务商开启二次验证，账号安全依赖邮箱本身。

## 2. 用户体验

采用现有全局登录恢复层，组件放入 `features/auth/`。首版无需新增 `/login` 页面：
保留 `/create`、项目、资产等当前 URL；会话过期时原地重新登录，避免页面跳转丢失未保存创作。

1. 未登录时在同一表单显示 GoodGood 标记、邮箱输入、“发送验证码”、六位验证码和“登录”；
   说明首次验证成功会自动注册，发送前验证码控件禁用。
2. 用户主动点击才发信；发送成功后锁定本次邮箱，发送按钮原位显示 60 秒重发倒计时，
   “修改邮箱”在同一表单显式重置。邮箱和验证码聚焦只改变边框，不使用选中阴影。
3. 验证码支持完整粘贴、数字键盘与系统一次性验证码提示；填写六位后点击“登录”。
4. active 用户继续当前页面；pending/suspended 用户进入既有状态界面。
5. 退出撤销服务端 Session 并清 Cookie；刷新后仍未登录。登录有效期沿用当前 30 天绝对上限。

默认不自动发送第二封，不因输入框变化或页面刷新发信。刷新后可通过同浏览器的短期挑战
在同一表单恢复验证码输入能力，不把邮箱/验证码放进 URL 或 localStorage。页面切后台再回来仍可继续。
更换浏览器需要重新获取验证码；在手机邮件 App 查码后回到原浏览器输入即可。
重新登录到另一个账号时必须先清除上个账号的内存数据；同账号才恢复原有创作上下文。

| 状态 | 页面行为 |
| --- | --- |
| 邮箱格式不正确 | 就地指出格式问题，不调用邮件服务 |
| 正在发送/正在验证 | 防重复点击，保留输入内容 |
| 已接受发送 | 提示已提交发送及查收垃圾箱；不声称已到达收件箱 |
| 验证码错误、过期、已用或被替换 | 统一提示“验证码无效或已过期”，允许按冷却时间重发 |
| 达到频率限制 | 显示何时可重试；不清空创作内容 |
| 投递结果暂不确定 | 提示稍等查收；收到的当前验证码仍可尝试，冷却后可重发 |
| 邮件服务/数据库故障 | 明确失败和支持编号，不伪装登录成功 |
| 收不到邮件 | 检查邮箱/垃圾箱、修改邮箱、重发、联系站长；不要求提交验证码 |

登录成功前不透露是否已注册或是否被暂停。有效验证码验证后才显示账户状态。
验证码只是证明收件箱控制权，不证明真人、实名或唯一用户；欢迎积分继续受审核边界保护。

## 4. 最小安全与存储设计

新增明确的 `GOODGOOD_AUTH_MODE=email_otp`；继续保留隔离本地 `local` 与迁移回退用 `oidc`。
生产不得启用 local/mock，也不得配置失败时降级。鉴权读取既有 `auth_sessions`，禁止把验证码
作为业务 API 凭据；退出逻辑需修正目前只在 oidc 模式撤销服务端 Session 的分支。

复用 PostgreSQL，不为首版增加 Redis 风控服务。建议新增以下小表，具体迁移序号在实施时
从最新 main 分配，避免和其他 worktree 的迁移冲突：

| 数据 | 最小用途 |
| --- | --- |
| `auth_email_bindings` | 唯一规范邮箱 → 唯一身份/owner；绑定验证时间；受审迁移来源 |
| `auth_email_challenges` | 随机 challenge ID、邮箱、浏览器绑定摘要、带密钥验证码摘要、发送状态、过期/消费/失效时间、失败次数 |
| `auth_rate_limits` | 邮箱/IP/全站时间桶及原子计数；IP/邮箱用带密钥摘要作键，避免到处存明文 |
| `auth_events` | 脱敏事件、支持编号、必要的内部 owner/投递编号、时间及结果；不存邮件正文 |

本地邮箱身份沿用 `auth_identities`，issuer 固定为 `urn:goodgood:email`，subject 为随机 UUID。
业务 owner ID 不变；不要用邮箱或网站域名生成 subject。沿用已有大小写不敏感邮箱比较规则，
明确做 trim/规范化并保存用户输入供显示；不去掉 Gmail 点号或 `+tag`，不按相似拼写合并。
对超长、CR/LF、多收件人和不支持的邮箱语法提前拒绝；本地与生产校验规则一致。

验证码使用密码学安全随机数生成 6 位数字；存储采用服务端独立密钥的 HMAC-SHA-256，绑定
challenge ID、用途和规范邮箱，并作恒定时间比较。仅普通 hash 或加盐不足以保护低熵验证码。
密钥不少于 32 个随机字节，和 SMTP 凭据分别从受保护文件挂载，只给所需服务；日志、错误、
镜像、浏览器、命令参数均不包含秘密。密钥轮换允许使未完成验证码失效，不撤销普通会话。

以下是低流量 alpha 的可调初始值，不是通用安全标准。限流是服务端强制、跨 Web 实例共享：

| 控制 | 初始值 |
| --- | --- |
| 验证码有效期 | 5 分钟，成功一次即失效 |
| 同邮箱发送冷却 | 60 秒 |
| 同邮箱发信 | 每小时 5 次、每日 20 次 |
| 同 IP 发信 | 每小时 20 次、每日 100 次 |
| 全站发信 | 每小时 100 次、每日 500 次，达到上限暂停发信并告警 |
| 同挑战错误验证 | 最多 5 次，耗尽后挑战失效 |
| 跨挑战同邮箱错误验证 | 30 分钟最多 10 次；重发/换浏览器不重置此计数 |
| 同 IP 验证请求 | 15 分钟最多 50 次，包含无效 challenge |
| 会话 | 沿用 30 天绝对有效期；退出/运营撤销立即失效 |

日预算使用明确的 UTC 日界；其他限流使用滑动窗口或相邻时间桶加权，测试边界突发。
预算先原子预留再发信，失败/超时也占尝试预算，防止通过失败绕过上限；不要用进程内计数。
无效请求也有入口请求限速与小请求体上限，不能靠创建随机邮箱/challenge 耗尽数据库。
IP 必须从已验证的实际 CDN→Nginx 信任链提取并规范化 IPv4/IPv6，只信任受控代理覆盖的头；
不能直接相信客户端的 X-Forwarded-For。上线前核对实际链路，不能从 DNS 注册商推断 CDN。
共享出口可能触发限流，运营可据真实记录调整；全站预算限制成本但不保证抵抗分布式拒绝服务。

同一邮箱只保留一个当前挑战。重发在邮箱锁内使旧挑战失效并创建新挑战；后到旧邮件不能登录。
跨浏览器请求不能取走另一浏览器的挑战；使用随机 HttpOnly/Secure/SameSite 短期 Cookie 绑定。
发码、验证、退出均要求同源 POST、受限 JSON 请求体、明确 Origin 检查和 CSRF 防护；
SameSite 只是辅助。所有认证响应 no-store；不返回验证码或邮件供应商原始错误。

验证成功时，在同一数据库事务内锁定/消费挑战、解析或建立身份、建立用户、幂等欢迎积分、
写入 Session 摘要和最小审计记录，提交后才发 Cookie。并发提交最多一次成功；业务事务失败
不留下已用验证码却未创建账户的半成品。失败计数必须独立正确提交，不能因抛错被回滚清零。
若数据库已提交但响应丢失，优先检查是否已有有效 Session，否则用户按冷却规则重新取码；
重复登录不得重复用户/积分。绑定已有其他身份的邮箱只走已批准迁移，不做运行时自动关联。

## 5. 投递、故障和日常运营

首版使用有超时的同步 SMTP 投递，发送总体期限暂定 10 秒；在网络发送期间不持有数据库锁。
先持久化挑战和预算，再调用供应商。SMTP 接受只是接收发送请求，不是最终投递成功。
记录 sending/accepted/unknown/failed：超时或进程中断视为不确定，不自动重试以免重复发信。
明确拒收标记 failed 并使当前挑战失效；未过期的 sending/unknown 挑战仍可用正确验证码验证，
处理供应商已接收但本地没收到确认的情况。旧请求的迟到结果只能更新自己的挑战，不覆盖新挑战。
用户可在 60 秒后主动重发，旧码随新挑战失效；登录和发信并发结果需用事务测试。

首版复用供应商投递记录/退信抑制和已有主机日志，不建监控后台。先人工检查退信、投诉、
发信量、SMTP 错误和验证码成功率；全站预算达到 80%、连续 5 次发送失败或清理失败产生
去重告警，通过已有主机告警方式送达站长，若未有可用通道则在上线前选定并验收。
邮件故障告警不能只依赖同一条故障邮件链路；不自动切换认证供应商或撤销全部会话。
本地候选现输出脱敏 24 小时汇总、精确 request ID 支持查询、清理心跳及稳定告警码；
ADR 0016 将定时采集和通知通道交给既有监控责任方，P3 上线前仍须连接并验收到站长。

上线前准备三类维护操作，默认 dry-run、精确目标、记录操作人和原因：

- 查看脱敏认证/发送汇总和指定支持编号；完整收件信息仅在受控运营边界按需查看。
- 临时关闭发信/新注册；既有有效 Session 继续使用，已经发出的有效验证码仍可按规则登录。
- 暂停已有账号并撤销该 owner 的所有会话；复用已有审核/恢复界面，不增设复杂账户后台。

关闭新注册时，未绑定邮箱可统一接受发码请求；验证所有权后才提示暂不开放注册，避免枚举。
Suspended 状态仍允许验证后看自己的暂停信息和退出，但不能创作或读取私有内容。
首版不新建自动退信 webhook；供应商抑制/投递查询能力必须在上线前验证，否则补最小本地
永久退信抑制，而不能反复给明确无效收件人发信。

每小时用同镜像维护命令清理过期/终态挑战（保留不超过 24 小时），过期限流桶 48 小时，
认证审计 30 天；不因清理删除 users、账本或业务数据。安全有效期由查询判断，不依赖清理及时。
记录失败并告警；清理任务必须在无流量时也执行。备份副本仍遵循现有备份保留策略，不承诺
主库清理时立即从历史备份擦除。初期站长每日看一次投递与错误汇总，按支持编号处理投诉。
清理成功在同一事务写入一个不含个人信息的 heartbeat；账户暂停在原有审核事务内只撤销该
owner 的有效 Session，恢复不会复活旧 Session。对应操作不需要加载 OTP 或 SMTP 秘密。

## 7. 从 Authing 切换与回退

推荐保留原测试账号的数据，给明确核对过的旧 owner 增加邮箱身份；用户允许清理测试用户，
但全库重置、批量删除和修改账本不是本次迁移的前提。这里选择“小范围受审绑定”，不做通用迁移平台。

1. 发布前读取真实生产身份/会话汇总，确认保留名单和邮箱控制权；优先确认站长账号可收码。
   本地测试只用合成名单。先备份并验证恢复，再执行受审增量迁移。
2. 按精确 owner ID 和核对后的邮箱清单 dry-run：拒绝重复邮箱、冲突绑定、缺失用户和未经
   核验的管理员映射。每条新增本地随机身份及邮箱绑定，保留原 Authing 身份、owner、角色、
   资产、积分与审核状态，不再发欢迎积分。执行需匹配清单摘要/预期行数，重复执行无额外写入。
   已实现工具要求每项 `mailboxVerified: true`，未绑定站长必须排在首项并额外设置
   `administratorVerified: true`；原始外部 reference 仅以 SHA-256 留在绑定审计字段中。
3. 增量 schema 与旧 OIDC 程序兼容；先准备支持两种模式的候选，正常情况下仅公开一种登录。
   对迁移名单先做短期、明确配置的试运行，名单控制由服务端执行；不伪造管理员 Cookie。
4. 先验证站长邮箱登录、后台访问、普通用户边界与真实邮件，再切生产 email_otp 模式；
   迁移窗口暂停新的注册绑定，避免 OIDC 与邮箱路径同时为同邮箱建立冲突身份。
5. 初次切换至少保留 Authing 应用、旧身份与秘密 7 天。建议维护窗口撤销旧 Authing 来源会话，
   用户重新邮箱登录，证明新链路可用；目标和数量预览后执行，不删除历史 Session 记录。
6. 桌面/手机真实验收通过后恢复正常注册，观察至少 24–48 小时的失败、发信量、用户反馈，
   若流量太少则补指定测试邮箱验证；再决定是否清理 Authing、Google 配置与旧域名。

回退必须区分用户：旧账号保留 Authing 映射，可恢复原 OIDC 配置重新登录；切换后新注册的
邮箱账号没有 Authing 身份，直接恢复旧镜像不能保证它们重新登录。保留 email_otp 能力的
已验证候选用于后续版本回退；第一次切换若核心认证故障，先暂停发信/注册并保留数据，
修复或恢复已验证的邮箱配置。仅在全部受影响用户都有有效回退路径时才恢复 Authing。
不自动按同邮箱造 Authing 关联，不通过删账号消除冲突，不降级 schema 或回滚整库覆盖新业务数据。
SMTP 暂时故障不影响已有有效 GoodGood 会话；认证证据泄露则按受影响身份撤销会话。

GG-028 的工具只迁移 issuer 文本，不能完成这次邮箱绑定迁移；其未发布源码不作为本方案依赖。

## 9. 上线验收清单

- 新邮箱首次验证只创建一个 pending 用户和一次 100 积分；并发与重复请求不重复发放。
- 老用户登录保持原 owner/角色/余额/资产；未迁移邮箱冲突有明确运营处理路径。
- 错误、过期、重放、旧码、跨浏览器码均被正确拒绝；重发不清空邮箱累计猜测限制。
- 发码/验证限流、多 Web 实例竞态、时间窗边界、伪造代理头、跨域 POST、小请求体限制有测试。
- SMTP 拒绝/超时/迟到/重复请求和数据库中途失败可恢复；不误报已送达、不把明文码写入持久层。
- 重启后挑战及预算仍生效；定时清理、关闭发信/注册、定向撤销会话和异常告警验证成功。
- Chrome 桌面、Android Chrome 与 iPhone Safari：完整输入/粘贴/切邮件 App/返回/退出。
  桌面设备模拟只证明布局，不能冒充真机；缺少真机时明确待站长补验收。
- QQ、163、Gmail、Outlook：各至少 3 次授权的测试投递，跨两个时段记录实际延迟、垃圾箱和失败；
  目标每次 60 秒内收到有效码。小样本不当作 SLA；目标用户常用邮箱反复失败即阻止上线。
- 正常/暂停/待审核与站长权限、跨 owner 读取、退出撤销、会话过期和换账号清理均通过。
- 完成文案与公开隐私说明的实际供应商/数据用途更新、支持渠道核验；不扩展完整 C6 工作。
- `npm run check:local` 在实现稳定后一次通过；真实依赖测试只在显式临时栈，无真实生图 Worker。
- 精确候选 CI/image/security、生产 preflight、既有 alpha gate、备份/恢复与回退证据齐全。
  必需的额外计费生图按发布范围单独确认；本任务邮件认证验收不自行触发生成。
