# 高频开发与新会话接续

这是一套轻量默认流程，不是要求站长每次填写的表单。
在 GoodGood 项目目录新开窗口后，直接描述需求即可；agent 负责恢复上下文。

## 1. 开始前：先恢复事实

1. 完整读根 `AGENTS.md`，再读 `CURRENT_STATE.md`、本文、
   `IMPLEMENTATION_PLAN.md` 和 `BACKLOG.md`；按任务加载专题文档。
2. 检查 `git status --short --branch`、`git worktree list`、近期提交，
   确认所在分支、未提交改动和当前检查点；[跨窗口交接](DEVELOPMENT_HANDOFF.md) 给出具体版本/启动/测试命令。如需远端事实，先安全 fetch。
   不将旧聊天中的“已完成/已批准”当作当前 Git 或生产证据。
3. 用户说“继续”：先匹配当前分支/任务卡的下一步；有多个可选任务才询问。
   用户提出新需求：新建任务，不自动继续 C6、支付或历史下一阶段。
4. 用一两句话说明理解、验收点及是否改变已有决定。可合理推断的小细节直接做；
   只有影响产品方向、权限/数据安全、成本或发布范围的缺口才集中提问。
5. 为新需求分配未占用的 `GG-xxx`（普通任务从 GG-004 起，900 段用于搁置项），
   建 `docs/tasks/GG-xxx-slug.md` 并更新 BACKLOG。用户不必提供任务编号。

## 2. 分支与数据隔离

- 从 IMPLEMENTATION_PLAN 指定并核验祖先的当前检查点开始 `feature/GG-xxx-slug`、`fix/GG-xxx-slug`
  或 `chore/GG-xxx-slug`；main只有包含该检查点时才适用。现有用户改动先辨认归属，不擅自 stash/reset/覆盖。
- 同一根目录同时只允许一个窗口编辑。并行任务用仓库外的独立 worktree，
  例如 `F:/goodgood-worktrees/GG-xxx`；不同窗口不能同时切换同一目录分支。
- 若目标分支已被其他 worktree 占用，进入那个目录或另建任务分支；不强行抢占。
- `archive/c6-deletion-content-safety-20260907` 是搁置快照，不是开发/发布基线。
  需要其能力时只选择明确依赖，审查迁移与测试，禁止整体合并省事。
- 本地只用本地身份、合成素材和隔离依赖。不下载生产数据库/R2素材/秘密。
  `work/` 内旧脚本只是历史工具，不因存在就有执行许可或可移植性。
- 历史 `.openai/hosting.json`、Cloudflare worker/Sites 入口不是当前生产目标；
  不因工具发现它们就改用其他托管服务或外部业务 skill。

## 3. 实现与验证

1. 先把需求归为 UI、契约、运行时、持久化或发布变化，记录最小范围、验收点和
   决策影响。改已确认决定先补 ADR；普通实现不制造无关 ADR，也不顺手扩展范围。
2. 先检查直接相关代码和测试，做行为完整的最小修改。只有验收必需或当前修改暴露了
   可复现缺陷，才增加恢复加固或重构，并在任务卡写明原因。
3. 迭代时先跑受影响模块的定向测试。实现稳定后只跑一次 `npm run check:local`；
   此后只有影响运行时代码、构建或测试输入的改动才重跑完整门禁。纯文档流程修改只跑
   文档契约测试与 `git diff --check`。
4. UI 预览用 `npm run dev:local`；持久流程才用本地 Compose。只有运行时、依赖、迁移或
   Compose 配置改变时才重建容器；纯文档或测试保护修改不重建。
5. 向数据库、队列写 fixture 的 opt-in 测试必须使用显式命名的临时数据库/栈，并确认
   没有真实 provider Worker 连接它。禁止依赖默认 URL，禁止让测试 outbox 进入真实
   O1Key Worker；需要真实付费调用时必须由站长明确要求该次调用。
6. 按风险补充接口/浏览器、权限隔离、积分和迁移测试，标注跳过项及原因。UI 预览成功
   不代表后端、真实模型、生产回调或跨账户隔离已经验证。
7. 交付一个可验收的最小变化；不把高频小改动扩成完整上线或无关配套工程。

## 4. 发布：一次明确的范围确认

“做需求”默认授权本地实现和验证，不自动授权上线。用户明确要求并批准某个
发布范围后，可连续执行该范围内步骤，不逐条重复询问。
新成本、删除/不可逆迁移、外部账户权限、额外流量变化需要相应明确授权。

1. 审查干净 diff、任务验收和依赖；合入 main 的仅是本次已验证变化。
   `main` 的 commit/CI/image 发布不等于生产部署。
2. CI 构建并检查一个不可变 Linux 镜像；记录完整 revision、digest、migration、
   runtime-config checksum。服务器拉镜像，不从工作目录源码构建。
3. 按 `DEPLOYMENT.md` 与 ADR 0024 使用**当前模式**的就绪证据，绑定精确候选。
   本轮整理暴露的 alpha 工具可移植性见 GG-003，下一次发布前必须处理。
4. 读取最新生产健康/备份/活跃任务，取得维护窗口批准。按 ADR 0091 在同一
   Compose 项目内处理旧任务/drain 和单 Worker 交接；不能为了快而重复提交计费请求。
5. 未来发布禁止 blue/green 槽位和 Nginx 上游切流。单槽位替换会影响生产，迁移必须
   向后兼容或另行确认恢复方案；失败只恢复旧应用镜像，绝不运行旧“清空转换”流程。
6. 通过正常登录路径完成与需求相关的冒烟，核对权限、积分、私有资产与错误行为。
   浏览器不可用就报告 API-only/待手动验收；不得伪造会话绕过登录并当作 UI 证据。
7. 失败按已审查且兼容的回退/维护方案处理；数据边界异常立即止损。
   更新 CURRENT_STATE、发布记录、任务卡，明确是否真正部署。

支付、全量删除体系、举报中心或大规模监控不是普通 alpha 功能开发的默认前置。
涉及这些领域的新需求仍需对应风险评估；不能用 alpha 名义省掉数据安全。

## 5. 中途保存与结束交接

- 用户确认重要取舍后立即写进任务卡/ADR，不等上下文压缩。
- 在阶段边界、长测试前、等待用户/外部条件前、结束/换窗口前更新任务卡：
  已做/未做、文件、最近验证、当前分支/worktree、阻塞和**可执行的下一步**。
- 同步 IMPLEMENTATION_PLAN 的唯一当前检查点，BACKLOG 只记优先级/状态和链接。
  未改变部署时明确说明；不要把本地测试数写成线上证据。
- 验证后提交任务相关代码和记录；经用户授权可推送/合并，不吞并别人改动。
  未能提交时写清未提交文件及原因。不要只在最后聊天回复里交接。
- 保持 CURRENT_STATE / WORKFLOW / IMPLEMENTATION_PLAN 每份不超过 150 行，
  根 AGENTS 不超过 170 行。细节移到任务卡；旧阶段移到 history，保留追溯链接。
- 已交付任务留下简短结论；积累较多后移到 `tasks/archive/` 并修复链接。
  不删除仍在使用的运维指引、测试和未发布源码来“精简”。

## 给新窗口的一句话

在 `F:\goodgood` 项目中打开新对话，然后直接写：

> 新需求：……。按项目约定完成本地实现与验证，先给我验收。

想继续中断工作可以写“继续 GG-xxx”；想发布可以在验收后写明要发布的任务。
若新窗口没有访问此仓库，先打开/选择项目，不能假设它自动继承其他窗口聊天。
