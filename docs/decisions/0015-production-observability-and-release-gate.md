# ADR 0015: Production observability and release gate

- Status: Accepted
- Date: 2026-09-04
- Superseded in part by: ADR 0016 for the observability vendor, collector, and
  notification transport
- Refined by: ADR 0019, which keeps this paid-production gate and adds an
  earlier no-checkout invitation-only seed-production gate
- Refined by: ADR 0021, which applies the same recovery objectives to the
  accepted single-host unpaid seed-production topology

## Context

M7 proved one immutable staging release, public health checks, rollback, and an
encrypted off-host PostgreSQL restore. It deliberately left active alerting,
production retention and recovery objectives, support correlation, and the
paid-production release gate to M8. The production domain, ICP filing, and
domestic Alipay merchant prerequisites are still external blockers, so M8 must
make useful progress without presenting staging evidence as production proof.

The application already writes some JSON events, but a browser-visible error
can receive an ID created after the failing request while the surrounding HTTP
request has no shared correlation ID. Host, application, provider, and backup
failures also have no unified outbound route. A staging-only mailbox would
create a second alert path that would be discarded at production.

## Decision

Use Grafana Cloud as the initial external metrics, logs, dashboards, and alert
evaluation plane. A pinned Grafana Alloy agent will collect container and host
signals without exposing a public metrics endpoint. Grafana's native WeCom
contact point is the sole initial outbound notification transport. QQ Mail and
any staging-only SMTP path are excluded. The contact-point credential and
telemetry write credentials remain host-managed secrets outside Git and outside
the application containers.

Application processes write one-line structured JSON to stdout. The production
web runtime creates a server-owned request ID for every request, returns it as
`X-Request-Id`, uses the same value in normalized error envelopes, and records
one completion event containing only method, normalized route, status, elapsed
time, and approved correlation fields. It never trusts a caller-supplied
request ID and does not log query strings, cookies, authorization values,
prompts, email addresses, signed URLs, object keys, or response bodies. The
request ID is also the customer-facing support ID. Authenticated requests may
add the internal GoodGood owner ID; generation work may add the job ID and
provider task ID. These identifiers are operational correlation data, not
browser credentials.

The first production dashboards and alerts must cover:

- public availability, HTTP 5xx rate, and p95 application latency;
- queue depth and oldest-job age, generation success/failure, end-to-end and
  provider latency, and customer-credit settlement;
- Authing callback failures and payment callback rejection/duplicate events;
- PostgreSQL connections/storage, Valkey memory, host disk/memory, and container
  restart/readiness state;
- R2 upload/download failures, ESA origin/cache failures, and backup freshness;
- upstream provider spend from the provider's usage evidence until a supported
  machine-readable cost feed is available. GoodGood must not invent cost data.

Alert rules use `environment`, `service`, `severity`, and stable alert-name
labels. They must group repeated events, send firing and resolved notifications,
and link to a checked-in runbook without including user data. Severity 1 pages
the primary and secondary operator immediately and requires acknowledgement in
15 minutes; Severity 2 requires acknowledgement in business hours within four
hours. No alert automatically retries a billable provider submission, restores
a database, grants credit, deploys, or rolls back.

For initial paid production, PostgreSQL has an RPO of at most one hour and an
RTO of at most four hours. Production backup scheduling and retention must meet
that RPO and preserve at least 14 daily, 8 weekly, and 12 monthly recovery
points in a separately encrypted repository. Application logs are retained for
30 days and metrics for 90 days unless a later legal/privacy review requires a
shorter period. Prompts, generated bytes, email addresses, credentials, and
signed URLs are excluded from telemetry.

ADR 0021 applies the same PostgreSQL RPO, RTO, and recovery-point retention to
the initial unpaid seed launch even though PostgreSQL is colocated on the small
application host. The final encrypted M7 staging archive is a conversion
rollback aid, not a production recovery point; retain it for seven days after
the clean production conversion passes, then delete it through the separately
approved exact-target cleanup.

The paid-production release gate fails closed until all of the following have
current evidence for the exact immutable image digest:

1. the repository gate, locked-dependency scan, finished-image import smoke,
   and image scan pass;
2. migration and runtime-contract labels match and the production preflight
   rejects local auth, fake payment, mutable images, and inline secrets;
3. a fresh backup and isolated restore meet the production RPO/RTO objectives;
4. dashboards receive a synthetic request and generation, every required alert
   has an owner/runbook, and a WeCom firing/resolved test is acknowledged;
5. the candidate starts separately, migrations run once, live/ready and public
   synthetic checks pass, and queue/database/credit invariants remain valid;
6. the compatible prior digest and configuration are retained and a rollback
   rehearsal passes without a schema downgrade;
7. ICP/domain, privacy/security review, support ownership, and the real domestic
   Alipay sandbox/merchant gates pass before customer checkout is enabled.

Grafana Cloud and WeCom account provisioning, secret entry, dashboard/alert
activation, and live delivery acknowledgement are operator evidence. Local
tests can prove structured-event shape, redaction, correlation, and fail-closed
configuration, but cannot claim those external controls passed.

## Consequences

- M8 can implement and verify correlation and telemetry contracts before the
  production domain and Alipay prerequisites are ready.
- The small production control plane does not host a second monitoring stack,
  but it depends on outbound access to Grafana Cloud and WeCom; local journals
  and health status remain the diagnostic fallback during telemetry outage.
- WeCom is an alert destination, not a store for prompts, user content, or
  credentials.
- The existing daily M7 backup policy remains valid staging evidence but does
  not meet the one-hour production RPO. Production scheduling must be proved
  separately before paid launch.

ADR 0016 later defers the Grafana Cloud, Alloy, and WeCom implementation to a
separately assigned monitoring agent. The request/support correlation,
recovery objectives, data exclusions, and paid-production release-gate
requirements in this record remain accepted.
